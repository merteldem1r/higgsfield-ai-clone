Favourites are built. Lint, typecheck and the build pass, but none of it has run against the database yet, because the migration isn't applied. I haven't tested it in a browser either.

One change from your spec, which you approved: instead of `toggle_favourite(p_asset_id)`, the function is `set_favourite(p_user_id, p_asset_id, p_favourite)`. The service role calls it, so `auth.uid()` is NULL inside and the user id has to come from the session, as with `start_generation`. Setting a value instead of flipping it means a retried or repeated request can't leave the server out of step with the heart on screen.

**SQL to run** (`supabase/migrations/20260923120000_favourites.sql`):
```sql
create function public.set_favourite(p_user_id uuid, p_asset_id uuid, p_favourite boolean)
returns jsonb
language plpgsql
security definer
set search_path = ''
as $$
declare
  v_favourite boolean;
begin
  if p_user_id is null or p_asset_id is null or p_favourite is null then
    raise exception 'set_favourite: p_user_id, p_asset_id and p_favourite are required';
  end if;

  update public.assets
     set favourite = p_favourite
   where id = p_asset_id
     and user_id = p_user_id
  returning favourite into v_favourite;

  if not found then
    return jsonb_build_object('ok', false, 'code', 'NOT_FOUND');
  end if;

  return jsonb_build_object('ok', true, 'favourite', v_favourite);
end;
$$;

revoke execute on function public.set_favourite(uuid, uuid, boolean) from public, anon, authenticated;
grant execute on function public.set_favourite(uuid, uuid, boolean) to service_role;
```
It doesn't take the `app_budget` lock. That lock is there to serialise credit changes, and favourites don't touch credits.

**What's built**
- **API:** `POST /api/assets/[id]/favourite` with `{ favourite: bool }`. It gets the user from the session via `getUserId`. Another user's asset returns the same 404 as a missing one, so asset ids can't be probed.
- **Optimistic updates:** there's one request per asset at a time. Clicks made while a request is in flight only change the value it will send next. If a save fails, the heart goes back to the last value the server confirmed and a toast appears.
- **Assets page:** a heart on each tile, shown on hover on desktop and always on touch. The Favourites sidebar item shows a live count, filters the grid and no longer has the "Soon" badge. Search works inside Favourites, and there's a "No favourites yet" empty state.
- **Lightbox and Image page:** the heart is in the lightbox (next to the close button) and on finished result tiles. To make that possible, `/api/generate` now also returns each asset's `id`, and the history query loads `id` and `favourite`. If the id lookup fails after a successful generation, it's only logged: the images come back without a heart, and the generation is not refunded.

**Things you should know**
- On Assets tiles, a favourited heart stays visible without hover so favourites are easy to spot. On Image result tiles it still only shows on hover, next to download. Tell me if you want those to match.
- In the Favourites view, unhearting an image removes its tile straight away.
