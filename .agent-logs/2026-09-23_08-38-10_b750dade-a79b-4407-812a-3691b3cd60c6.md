One change from your spec, which you approved: instead of `toggle_favourite(p_asset_id)`, the function is `set_favourite(p_user_id, p_asset_id, p_favourite)`. The service role calls it, so `auth.uid()` is NULL inside and the user id has to come from the session, as with `start_generation`. Setting a value instead of flipping it means a retried or repeated request can't leave the server out of step with the heart on screen.

**SQL to run** (`supabase/migrations/20260923120000_favourites.sql`):
```sql
create function public.set_favourite(p_user_id uuid, p_asset_id uuid, p_favourite boolean)
returns jsonb
language plpgsql
security definer
set search_path = ''
as $$
declare
  v_favourite boolean;
begin
  if p_user_id is null or p_asset_id is null or p_favourite is null then
    raise exception 'set_favourite: p_user_id, p_asset_id and p_favourite are required';
  end if;

  update public.assets
     set favourite = p_favourite
   where id = p_asset_id
     and user_id = p_user_id
  returning favourite into v_favourite;

  if not found then
    return jsonb_build_object('ok', false, 'code', 'NOT_FOUND');
  end if;

  return jsonb_build_object('ok', true, 'favourite', v_favourite);
end;
$$;

revoke execute on function public.set_favourite(uuid, uuid, boolean) from public, anon, authenticated;
grant execute on function public.set_favourite(uuid, uuid, boolean) to service_role;
```
It doesn't take the `app_budget` lock. That lock is there to serialise credit changes, and favourites don't touch credits.
