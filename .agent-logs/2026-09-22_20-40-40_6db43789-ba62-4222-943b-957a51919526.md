## The migration: review before you run it
The file is `supabase/migrations/20260922204453_walking_skeleton.sql`. Paste the whole thing into the SQL editor. What it does:

- **Tables:** the five tables from PLAN.md, with checks on credits (never below 0), batch size (1–4), prompt length (1–2000) and status. `credit_ledger` has `UNIQUE (generation_id, reason)`, so a generation can only be refunded once.
- **Grants:** Supabase stopped auto-granting new tables to the Data API on May 30, 2026, so the migration sets every grant explicitly:
  - Any visitor (the `authenticated` role) can only read their own profile, generations and assets, enforced by RLS on `auth.uid()`.
  - The ledger and budget tables can't be read by clients at all.
  - The server's secret key can only read tables, never write them. Every write goes through the functions, so app code can't update credits even with the secret key.
- **Signup trigger:** creates a profile with 6 credits, a handle like `renderingraven1592` (retried if taken), and a matching ledger row.
- **Credit functions:** `start_generation` and `fail_generation` work as PLAN.md describes, including the 3-minute cleanup of stuck requests and the daily budget reset. Each takes a lock on the budget row first, so parallel calls wait in line instead of deadlocking. `EXECUTE` is revoked from `anon` and `authenticated`, and only the service role can call them.
- **Storage bucket:** yes, the migration creates it: a public `generations` bucket, 10MB limit, jpeg/png/webp only. No upload policies, so only the server can write to it.

## Choices I made that you should know about
- **I added a third function, `complete_generation`.** Marking a generation succeeded and saving its images happen in one step. If the image count doesn't match the batch size it errors, and the whole batch gets refunded. That's the safe behaviour until partial refunds exist for batches.
- **The server checks the user with `getUser()`, not `getClaims()`.** Supabase now recommends `getClaims()`, but `getUser()` asks the Auth server, which catches revoked sessions; it adds about 100ms. The route also accepts an `Authorization: Bearer <token>` header, so step 2's curl tests will work.
- **No `proxy.ts` yet.** Supabase recommends one so server-rendered pages can refresh login tokens, but nothing server-rendered reads the session yet. It'll be needed when the credits pill in the nav lands (step 3).
- **Images flagged by fal's safety checker** count as a failed generation, and the credits are refunded.
- fal calls time out after 45s, leaving room to refund before Vercel's 60s limit.
- `ip_hash` stays empty until step 2. An unsalted IPv4 hash is easy to reverse, so it needs a salt env var alongside the per-IP cap.
- Package versions are pinned exactly. I briefly installed `server-only`, then removed it, because Next.js handles that import itself.
